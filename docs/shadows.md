# How the game draws shadows (reverse notes, 2026-10-21; complete map 2026-10-24)

## The complete map in one page (2026-10-24: every shadow / light function of game.exe read; details with all offsets and constants in _cpr/shadows/casters.md, receivers.md, terrain-light.md)

There are only four kinds of "shadow", and none of them is a depth-based shadow:
1. **Caster bitmap draped on the TERRAIN** (units, trees, buildings, stones, torches, levers: `CObject3DClientSpecific::Render` 0x51CE60, last pass of `CWorldClient::RenderObjects`). The caster's triangles are projected along the light onto the horizontal plane through the owner's origin, rasterised FLAT (0xF000 in a 64 x 64 A4R4G4B4 scratch surface, one winding, no clipping; 3x3 box blur when `ShadowQuality` == 2), copied with `IDirect3DDevice7::Load` into the owner's own 64 x 64 texture and draped over the TERRAIN triangles inside the prism of the light through the bitmap's rectangle (`RenderShadowVolume` 0x56C750 -> `CTerrain::BuildShadowReceiverMesh` 0x6CCF20; the receiver mesh has no depth test, any terrain triangle in the prism is shadowed). Drawn with diffuse 0x80FFFFFF (alpha 128 = at most 50 % dark; units: unit alpha x 128), z x 0.9999, z-write off. The bitmap's extent is stretched independently in x and y to the owner's own footprint (non uniform). Static objects cache the bitmap (refreshed about every 8 frames by the age rule), units recompute every frame.
2. **Terrain on terrain**: the per-vertex sun ray march (`TraceSunRay` 0x6C92C0, up to 95 Bresenham steps over the vertex heights, binary, hard-edged), only when the hidden registry option `EnableSelfShadowing` = 1 (retail 0; `LoadZone` clears terrain flag 0x10 otherwise). No object is ever in it.
3. **Print decals** (blood, footprints, scorch: `CPrintDecal::Render` 0x6CEDE0, formerly misnamed `CBridgeShadow::RenderShadow`) reuse the receiver mesh with the light straight down. They are not shadows.
4. **Lighting itself carries no occlusion**: terrain colours are computed on the CPU per vertex (`diffuse = max(ambient, sun N.L, every point light)`, FVF 0x1C4 pre-transformed vertices), units / objects in 3DfpFPU.dll (`min(1, emissive + max(ambient, N.(-D) sunDiffuse, point lights))` x `ObjectsLightingCoeff` 2.0). Point lights are never shadowed.

What this means: **objects never shadow other objects or units; units and objects never shadow anything but the terrain; terrain never shadows objects.** The object-receiver branch of `RenderShadowVolume` (buildings, bridges) walks `CWorldClient+0x1F4`, a list nothing in the exe ever fills (dead code), and the textured caster fill (2DintMMX slot 9) needs `CTexture+0x60` which nothing sets (dead too).

Sun and time of day (needed by any replacement): the sun is ONE directional `CLight` (kind 0x2E, `DAT_007af07c` = render globals 0x7AF060 +0x1C), rewritten every frame by `CWorldClient::UpdateDayLight` 0x566360: hour = `fmod(tick x world+0x20 + world+0x1C, 24)`; travel direction D = (cos az cos e, sin az cos e, -sin e) at light +0xD4/+0xD8/+0xDC with az = hour/12 pi and elevation e 30..75 deg (30 at 04 h and 20 h, 60 at noon, 75 at 00 h: the sun is NEVER below the horizon, night only darkens the colours); colours from `config/lights<[cave]><world>.ini` (24 entries each for `[sunlight]`, `[ambient]`, `[sky]`, linear interpolation) into light +0x98..+0xA0 (sun) and CWorldClient +0x6AC.. (ambient; 0.8 x sun when the table entry is 0,0,0). Indoors D = (0.5, 0.5, -0.7071). Per-frame camera: `CCamera` 0x79B2A8 (near 2.0, far 100.0, fov 0.8976 rad at the rig; `Mat4_Perspective` 0x4F0E80 = standard perspective, `Mat4_Viewport` 0x4F1370).
Frame order: sky, terrain opaque, objects and units (buckets), prints, SHADOWS (last of `RenderObjects`), water, effects / particles. Everything is pre-transformed on the CPU (3DfpFPU.dll) and drawn with `DrawIndexedPrimitive` (FVF 0x1C4; about 200 opaque draws, 30,000 triangles / 84,000 vertices and 65 z-write-off draws per frame in the multiplayer base, measured with um.dll's `UM_TRACE_D3D`).

Settings (registry `Shadow Settings`, AppSettings 0x79BC70): `ShadowQuality` 0x79BD0C (0 off, >0 on, 2 also blurs; no widget in the options screen), `UnitShadow` 0x79BD14 (typeId 0x50), `FloraShadow` 0x79BD1C (0x52 trees), `BuildingShadow` 0x79BD18 (every other typeId, 0x54 buildings included: 0x54 is CBuilding, not "foliage"); `HeroShadow`, `OtherShadow`, `EnableDynamicLights`, `ShadowingFreq` are stored and never read. The terrain relight rate is `LightingFreq` / 66.

Corrections to the older sections below: the unit-shadow light vector is built only from the light manager (`DAT_007AF230..238` is never written; start (0,0,0), sun + nearby point lights, clamped to >= 20 deg elevation); the light vector given to `RenderShadowVolume` is the travel direction (z < 0), so the "sun vector" above is its negation; the SkyMesh_* functions around 0x4D7F50..0x4D89A0 are the ShadowProjector / ClipBuf; the terrain relight is not "nearest first" (the sort comparator reads its arguments directly: arbitrary order); `CWorldServer::SetLighting` is really `SetWind`; the 0x200 in the target descriptor is the source map's pitch.

## The replacement: sun shadows (um-engine 0.11.0 `SunShadows`, d7vk.dll; 2026-10-24)

With D7VK the shadows are now REAL: the game's draws (about 200 opaque draws, 30,000 triangles a frame) are also drawn into a 2048 x 2048 depth map seen from the sun, and a full-screen pass
darkens the colour buffer where the sun does not reach. Terrain, objects and units cast on and receive from each other (a gate on the ground, a tent on the fence, a unit on a wall), alpha-tested textures (trees, grass) cut leaf-shaped shadows, the ground is
not painted: the shadow follows the surface. The darkness is the game's own ratio of ambient to sun at that hour (about 43 % by day, faint at night: the sun's colour is nearly the ambient colour then), so shadows
follow the day / night cycle and the sun's path (the sun object `0x7AF07C`, updated every frame by `UpdateDayLight`). The game's own projected bitmap shadows are switched off while this works (world flag 0x200 cleared every frame).
How: um-engine (`world_shadow.cpp`) calls D7VK's exports `UmShadowBegin` (a call site in front of `CTerrain::RenderOpaque`, 0x56A06B) and `UmShadowEnd` (after `CWorldClient::RenderObjects`, 0x56A080, before water and particles) with the sun, the ambient colour, the inverse of the
pipeline's screen mapping and the visible ground area; D7VK records every depth-writing `DrawIndexedPrimitiveUP` in between (`tools/d7vk/um-shadow/`). The vertex shader turns the game's pre-transformed vertices (x, y, z, rhw) back into world space with one matrix.
The screen mapping that matters (found by fitting the terrain sectors' world vertices against their transformed records): the matrix stack at `g_0x7AF068 + 0x14` (viewport x projection, including the 0.75 widescreen x scale) times the view stack at `+0x5C`; the projection stack at `+0x44` still holds the 4:3 matrix and is NOT what the pipeline uses.
Measured (gamescope rig, the multiplayer base): main thread 8.5 ms per frame with the game's own shadows, 4.9 ms with these (the CPU rasteriser, its 64 x 64 uploads and the receiver meshes are gone; the GPU does the work).
um-engine.cfg: `SunShadows=true`, `SunShadows::MapSize` (1024 / 2048 / 4096), `::Strength` (0..1), `::Extra` (extra darkness), `::Bias`, `::SlopeBias`, `::Margin`, `::Height`, `::Indoor` (caves keep the game's shadows), `::Debug` (research views: 1 shadow term, 2 lit fraction / sun angle, 4 normals, 5 world position; the file is re-read once a second).
Limits: needs d7vk.dll (the mod's default DDRAW_DLL); casters off screen are missing (the game clips triangles to the screen before they reach D3D), water and particles are not shadowed, point lights (torches) cast no shadows.

## Older notes (2026-10-21; still valid unless corrected above)

Read from game.exe (Ghidra decompile) and 2DintMMX.dll, checked on the test rig with um.dll's `UM_TRACE_D3D=1` tracer (`um_trace.cpp`: draw states, and the first shadow textures and meshes dumped to um-shadow-N.raw / .txt).

## Units (`CObject3DClientSpecific::Render` 0x51CE60, seed name UnitShadow::Render)
Per unit with shadows on (`g_0x79BD0C` > 0; per kind `g_0x79BD14` units, `g_0x79BD1C`, `g_0x79BD18` others), every frame:
1. the effective light direction: the sun (`g_0x7AF230..238`) combined with the point lights (objects of type 0x31) near the unit;
2. each figure part's triangles are projected to 2D in light space (`CFigure::EmitTriangles2D`) into a point buffer;
3. a scratch texture ("Format25", `CTextureManager::GetOrCreateFormat25`) is locked, cleared (8 KB = 64 x 64 x 16 bit) and the silhouette polygons are filled; the useful data is the top 4 bits of each 16-bit pixel (16 alpha levels, `0xF000` = full shadow);
4. in shadow quality 2 (`g_0x79BD0C == 2`) two separable 3-tap box blurs run over it (2DintMMX.dll, vtable slots 11 and 12 = 0x10003300 vertical, 0x10003400 horizontal, `* 0x5556 >> 16` = divide by 3, `& 0xF000`);
5. the texture is uploaded with `IDirect3DDevice7::Load` into the unit's own 64 x 64 video texture (`this + 0x7C`);
6. `CWorldClient::RenderShadowVolume` (0x56C750) builds the RECEIVER mesh: the terrain triangles inside the shadow volume of the light (`CTerrain::ClipAndAddTriangle`, clipped to the frustum), and, when asked, the triangles of the objects in the volume (bridges, buildings); the mesh is textured with the shadow texture (projective u, v in 0..1).

Draw state of the shadow mesh (traced): pre-transformed vertices (FVF 0x1C4, the game's own T&L), triangle list, Z test on, Z write off, alpha test off, alpha blend SRCALPHA / INVSRCALPHA, texture 64x64 16 bit, MAG / MIN filter LINEAR, address mode WRAP, COLOROP / ALPHAOP MODULATE.

## Terrain
The terrain has its OWN per-vertex sun shadow: `CTerrain::SetSunLight` 0x6C8ED0 (ray slopes from the light direction, relight scheduling), `CTerrain::TraceSunRay` 0x6C92C0 (a Bresenham walk along the sun direction over the sector grid, a vertex is shadowed when a vertex of the path is higher than the ray), `TerrainSector_LightVertexSun` 0x6C36B0 (ambient + sun per vertex). So terrain-on-terrain shade exists, at vertex resolution (cell-sized steps), and the unit / object shadow textures are drawn on top of it independently.

## What the tracer showed
The shadow texture is a smooth blob (blurred edges, ~3 px), the mesh follows the terrain relief. The cell-sized "crenellated" edges seen in some screenshots are therefore probably the terrain's per-vertex sun shadow (or the 64 x 64 resolution on very large casters), not the unit texture's filtering: to be separated by turning the game's shadow setting off at that spot.

## Footprints (not shadows) and the "pixelated and smooth" look
Footprints, blood and scorch marks are terrain decals (`CWorldClient::AddTerrainPrint` / 2 / 3, `CFootPrint`, `CBloodPrint`, `CFirePrint`; records built from terrain triangles clipped to the print's area, like the shadow receiver mesh), textured from the atlases `footprints`, `bloodprints`, `fireprints`. `prints.db` only holds opacity, lifetime and fade-out per terrain type and weather; the print's size comes from the unit's footprint type.
The crenellated, stepped look of a giant creature's footprint (ice golem) is in the ART: HD Lands' `HDTexRes/t_world_res/footprints.mmp` (1024 x 1024 DXT3, alpha only) has several large tiles that are low-resolution art with flat half-transparent 8 x 8 cells along their edges, magnified by the creature's size. A cleaned atlas (smoothing only around those cells) is in `_cpr/footprint-fix/`; the mod does not ship it (a report for the HD Lands authors).

## Unit shadow resolution (um-engine 0.6.0, `UnitShadow::Resolution`)
The 64 x 64 of the unit shadow texture is written as constants in game.exe: the two texture creators (0x692010, 0x692140: width / height), the silhouette scale `63.0 / extent` (two `fdivr` operands in Render), the clearing of the scratch texture (`mov ecx, 0x800` dwords), the two blur calls (`push 0x40` x 4) and the `0x200` in the target descriptor given to 2DintMMX's polygon drawer. um-engine patches all of them at once when the cfg value is 128 or 256 (`shadow_res.cpp`; all or nothing, byte-checked). Tested at 128 on the rig: the shadows draw correctly and the edge is only slightly smoother; the user judged the default 64 "just fine", so it stays off. 256 and the 0x200 = 8 x size guess are untested.

## Terrain and time of day (recon)
- The sun is live: `CTerrain::SetSunLight` (0x6C8ED0) takes the sun light object and the ambient colour, derives the ray slopes and per-step offsets from the light direction and, with a relight budget (`SetRelightBudget`), schedules the lit sectors for relighting with staggered countdowns (nearest first). So when the time of day moves the sun, the per-vertex terrain shadows follow, sector by sector.
- The per-vertex trace (`TraceSunRay` 0x6C92C0, `TerrainSector_LightVertexSun` 0x6C36B0) is binary: a vertex is either lit by the sun or gets the ambient colour only; the sun is ignored when its light +0xDC is positive (below the horizon). It runs only when the terrain flag +0x94 & 0x10 is set (`CTerrain::Load` sets +0x94 |= 0xFFFF, so it is on after every load). Its resolution is the terrain vertex grid (one step = one vertex), which is why terrain shadows are cell-sized and hard-edged.
- Unit / object shadows (Render 0x51CE60) are separate: a texture draped over the receiver mesh, with the light direction made of the sun plus nearby point lights (type 0x31); shadow quality is per kind (units 0x79BD14, kind 0x52 0x79BD1C, others 0x79BD18).

## The game's own terrain shadow is a hidden option, and um-engine can soften it (um-engine 0.7.0, `TerrainShadow::Softness`)
- The terrain sun shadow (TraceSunRay) runs only when the registry value `EnableSelfShadowing` (Terrain Settings, next to `ShadowingFreq` = the relight rate and `EnableDynamicLights`) is 1; it is 0 in the stock settings, so by default the terrain never casts shadows on itself. CWorldClient load (0x567AB0) turns the terrain flag 0x10 off when it is 0.
- With it on, the shadow is hard-edged at the vertex grid. `TerrainShadow::Softness=N` (um-engine.cfg) redirects the one TraceSunRay call (0x6C389F) to `terrain_shadow.cpp`: the ray is traced at the vertex and at four heights up to N game units above it, and the sun is scaled by the fraction that reaches the vertex, so a vertex that only just grazes the relief is partly lit. TraceSunRay's argument is the VERTEX (x, y, z floats), not a height. Heights below the vertex are not sampled (a point under the ground is always shadowed by its own cell).
- Compared on the rig at 17.5 h (base, gate shadow): `_cpr/shadow-compare/terrain-shadow-softness.png` (off / 1 / 2.5): 1 softens the edge a little, 2.5 more and makes the shadow fainter. Cost: 5 traces per relit vertex (relights are staggered by the game).

## Why bush and tree shadows are blocks, and why a shadow falls through a cliff (user report 2026-10-21, z9xq1)
- **Blocks.** `CObject3DClientSpecific::Render` rasterises a caster's triangles into the 64 x 64 shadow texture. Its first texture can drive a TEXTURED fill (2DintMMX vtable slot 9: the source is a 256 x 256 map of 16-bit pixels, bit 15 = opaque, from `texture +0x60` when the texture's flag `+8 & 0x2000` is set; the row stride 0x200 is the source's, not the shadow's); the original 16-bit textures kept such a copy, but the DXT textures of HD Lands / the mod never do (checked on the rig: no caster texture has the flag), so every caster is filled flat: a bush casts the silhouette of its whole mesh. um-engine 0.8.0 `ShadowAlpha::Textured` (shadow_occlusion.cpp) redirects the pick (0x51DA50) to `UmShadowAlphaMap`, which decodes the DXT1 / DXT3 / DXT5 alpha of the texture's surface (the game's own lock) into such a map (mean alpha of the covered texels, solid above 50 %). Foliage (caster kind 0x54: 1024 x 1024 DXT1, ~80 % solid) gets holes; many large textures decode as fully solid (their leaves are not in the first texture or have no DXT alpha), unit textures are left alone. Off by default.
- **Through cliffs.** The receiver mesh is every terrain triangle inside a prism extruded from the caster along the light (`RenderShadowVolume` 0x56C750 -> `CTerrain::ClipAndAddTriangle` 0x6CCF20), with no test whether the terrain between the caster and the receiver blocks the light, so a bush on a plateau shadows the ground behind the cliff. A hook at the call (0x51E08B, `UmShadowVolumeCall`) runs after the mesh is built and has the unit in ebx: its arrays are `+0x4C` (vertices, 16 bytes each: world x, y, z, w), `+0x50` (count) and `+0x5C` / `+0x6C` / `+0x70` (the rest: layout still to confirm). The next step is a ray test from each receiver vertex towards the sun against the terrain heights (`CTerrain::GetVertex` 0x6C85A0) and the removal of the triangles that are blocked.

## Terrain occlusion of unit / flora shadows (um-engine 0.8.0, `ShadowReceiver::Occlusion`: REMOVED 2026-10-21, kept here as the design)
`CTerrain::ClipAndAddTriangle` (0x6CCF20) walks every terrain cell under the shadow prism and hands the two triangles of each to `Clip_TriangleToFrustumA` (0x4D8490, thiscall, three `float[3]` vertices x, y, z) at 0x6CD505 and 0x6CD516. um-engine redirects those two calls (and the `RenderShadowVolume` call at 0x51E08B, which gives it the light direction) to `UmClipTriangle`, which leaves out a triangle when two or more of its corners are in the terrain's own shade: ground the terrain keeps from the sun is already dark, so a caster's shadow does not belong there (a bush on a plateau no longer shadows the ground behind the cliff). Whether a terrain vertex sees the sun is a ray march towards the sun over the game's own heights (`GetVertex` 0x6C85A0, 1-unit steps, up to 48, slack 0.3 + 0.04 t), computed ONCE per vertex and kept in a map the size of the terrain (the sun is a fixed vector: (-0.23, 0.30, 0.93) in the rig at every game hour; the game's shadow light does not follow the time of day). First version (a ray march per triangle, four samples each) cost the user 35 FPS in the Gipath lobby; the cached one measured 0.38 us per triangle, ~1250 triangles a frame in the rig lobby (~0.5 ms). Checked on the rig with the zone9x terrain as the base: relief casters lost 10-50 % of their receiver triangles (the first, per-caster version); on screen the change was small because the game's sun is 68 deg up, so only tall cliffs matter (the user confirmed it works on z9xq1).

## Things tried and removed (2026-10-21)
- `TerrainShadow::Softness` (a penumbra for the terrain's own per-vertex sun shadow: the ray traced at five heights, the sun scaled by the fraction that gets through): no visible difference, because the game blends the vertex lighting across each cell anyway. Removed. Note that the stock game never casts terrain shadows at all (`EnableSelfShadowing=0` in the registry's Terrain Settings).
- `ShadowAlpha::Textured` (leaf holes in foliage shadows through the DXT alpha, fed to the game's textured fill): no visible difference. Most trees' first texture has no usable alpha, and the shadow bitmap is only 64 x 64; a real fix needs one alpha map per mesh part. Removed.
- `UnitShadow::Resolution` works (checked: the unit's own shadow texture is 64 / 128 / 256 squares) but the difference on screen is slight; it stays an option.
- `ShadowReceiver::Occlusion` (above) was removed too: it worked (the user saw it on z9xq1) but still cost a lot of FPS in the lobby and the result was not good. Decision (user): the whole shadow code of game.exe will be reversed and replaced later by clean, fast code (receiver mesh, caster silhouette, terrain occlusion, alpha, resolution together) instead of patching around it.
